# Куда идёт лаунчер: разбор их системы

Дата: 2026-11-18. Источник: тег `v0.4.12-nightly.261118100` репозитория
`Open-BFME/openbfme-godot` (18.5 МБ, скачан через codeload) и наше закреплённое
дерево `bf06a22` (`tools/prepare.py`).

## Что у них есть (по факту, не по описанию)

| Что | Факт |
|---|---|
| Лаунчер | **Godot 4.7-проект**, 22 799 строк GDScript (`launcher/scripts/`), а не C#/WPF |
| Релизы | `manifest.json` + подпись Ed25519; каждая посылка проверяется по SHA-256 |
| Канал | `build_info.json` внутри сборки: `repo`, `release_key`, `version` — **свой GitHub-репозиторий задаётся при сборке** |
| Сам лаунчер | Бинарник 39 МБ (`openbfme-launcher-*-windows-x64.zip`), обновляет себя сам |
| Игра | Отдельная посылка `openbfme-*-windows-x64.zip`, 86 МБ |
| Моды | Свой экран, каталог с bfmeladder.com, установка в `user://mods/<guid>/`, запуск с `--mod=` / `--mod-install=` |
| Лицензия | GPL-3.0 |

## Три уровня «их системы» — их нельзя смешивать

1. **Формат релиза.** Манифест + подпись + SHA-256 + канал + самообновление.
   Переносится на что угодно и ничего не стоит: это про то, как раздавать файлы.
2. **Их лаунчер.** Готовый бинарник, умеет всё: обновления, моды, реплеи, лобби.
   Работает **только с их игрой** (`godot/` современной ветки, C++-движок
   `engine/src`). Наш мод он не запустит: у нас GDScript-патч к другой игре.
3. **Их игра.** C++-движок, читает ретейл-файлы RotWK 2.01 / BFME2 1.06
   **напрямую**, сверяя с пинами. Никакой конвертации, никакого FFmpeg, никаких
   бандлов, никакого часа на первый запуск.

## Наш мод и их игра — это разные игры

Наше дерево — `legacy-final` (`bf06a22`, версия 0.2.13): GDScript «retail slice»,
`game/src/retail_slice/*.gd`, 630-строчный патч по 14 файлам (команды
`ar_draft`/`ar_reroll`, сид, лобби, HUD).

В их современной ветке (`v0.4.12`) **нет** ни `game/src/`, ни `retail_slice/`,
ни `scripts/modes/`. Их лаунчер запускает `openbfme.gdextension` (C++-движок).
Наш патч там не к чему прикладывать — папки, которые он правит, не существуют.

**Вывод:** отпустить наш мод на их лаунчере нельзя без порта мода на их движок.
Это не про лаунчер, это про игру.

## Что из их системы применимо к нам уже сейчас

1. **Релиз-канал вместо сборки на машине игрока.** Наш мод — это GDScript и
   данные, они не зависят от чужого бинарника. Собранное дерево можно раздавать
   одним архивом с `manifest.json` + SHA-256, как они: игрок ничего не собирает,
   первый запуск — распаковка, а не час конвертации.
2. **Подпись Ed25519.** У них ключ уже в GPL-исходниках; можно взять их схему
   целиком, чтобы игрок не мог получить подменённый архив.
3. **Самообновление.** Игрок один раз скачал — дальше кнопка «Обновить».
4. **Отмена в любой момент.** У них `request_stop("pause"|"cancel")` на уровне
   HTTP: пауза сохраняет `.part` и продолжает с `Range`. Наш фикс (кнопка
   «Остановить» + `taskkill /T`) закрывает только «закрыть окно», а не «продолжить
   загрузку завтра» — это следующий шаг.

## Чего у нас не будет никогда

В их релизах **нет файлов игры** (ни ретейла, ни конвертированных данных): они
читают установку игрока. Мы конвертируем и храним данные локально — по той же
причине: чужие файлы нельзя класть в публичный релиз.

## Первый релиз (v0.3.0)

`v0.3.0` — первый релиз с деревом. Проверено **по дайджестам из GitHub API**,
без скачивания (в песочнице release-assets недоступны, это известное
ограничение, а не сбой):

| Файл | Размер | Совпадает с локальной сборкой |
|---|---|---|
| `tree-v0.3.0.zip` | 17 112 192 | да, `33386efc…` |
| `tree.json` | 294 | да, байт в байт, `0b0bcf47…` |

Манифест указывает на `…/download/v0.3.0/tree-v0.3.0.zip` с тем же дайджестом.
Раньше `latest` был `v0.2.0` без `tree.json` — то есть лаунчер честно падал в
локальную сборку. Теперь `latest` = `v0.3.0`.

## Что уже сделано (эта ветка)

**Раздача дерева из CI.** `tools/build_tree_package.py` собирает дерево один
раз (исходники по пину → `patches/*.patch` → наша `game/`) и выпускает
`tree-<версия>.zip` + `tree.json` с SHA-256. `launcher/start/tree_package.py`
скачивает манифест, проверяет размер и дайджест, распаковывает и проверяет, что
это действительно **наш** мод, а не голый OpenBFME. Шаг `prepare` сначала идёт
этим путём и только при его отказе собирает дерево локально — с честным
объяснением, почему.

Что это даёт: 17 МБ исходников и наложение патча уходят из первого запуска
игрока. Проверено на настоящем пинованном архиве: 16.3 МБ, распаковка 0.5 с,
второй запуск — «исходники уже собраны».

Чего это **не** даёт: конвертация ваших файлов остаётся на вашей машине.
Её результат — производная от ретейл-данных, в публичный архив их класть
нельзя (та же причина, по которой их релизы не содержат файлов игры).

## Решение (предложено)

Разделить два вопроса, которые сейчас смешаны:

* **Лаунчер** → переходит на их модель: тонкий клиент, который скачивает готовый
  архив мода по манифесту, проверяет SHA-256, распаковывает и запускает. Ни
  `prepare.py`, ни FFmpeg, ни конвертации на машине игрока. Кода становится
  меньше, а не больше.
* **Игра** → остаётся на нашем закреплённом `legacy-final`, пока мод не портирован
  на их движок. Порт — отдельная задача, и она про игру, а не про лаунчер.

Второй вариант — портировать мод на их движок и встать на их лаунчер целиком.
Это единственный путь, на котором мы «как они» по-настоящему, но он означает
переписать рандомайзер под C++-движок и ждать, пока их мод-API покроет нужное.
